1. The goal

Think of a mailbox with a little red flag. The flag tells you "something is inside" without opening the door. We want that flag on a phone.

2. Two hard walls

Wall 1: Android shows a dot

On Android 8 and newer (Pixel, stock Android) the icon gets a small dot, not a number. Only some makers' launchers (Samsung, Xiaomi) can show a number, and only through an extra plugin. This is Android's own rule, so no framework beats it on a Pixel.

Wall 2: iPhone push costs $99

Every iPhone app that is not a web app needs the Apple Developer Program ($99 per year) before it may receive push messages. A free account cannot turn push on. A web app added to the Home Screen (a PWA) is the only free way to get a numeric badge on iPhone.

3. Why a closed app needs a push

A phone puts a closed app to sleep and cuts its open connections (iOS does this to sockets). A sleeping app cannot hear the gateway. So the gateway must ring the phone's own doorbell: the phone maker's push service.

The gateway needs three small jobs: remember each phone's push address, keep an unread count per person, and send the push. No Apple account or Firebase SDK is needed for the PWA route.

5. Pros and cons, Android and iOS apart

PWA

Android

  • + Free, install prompt, no store.
  • - setAppBadge does nothing on Android; dot comes from a shown notification.

iOS

  • + Only free numeric badge; works from the push handler when closed.
  • - User must add it by hand (iOS 16.4+) and allow notifications; user can hide the badge in Settings.

Can the app icon itself be redrawn with the number? No: iOS copies the icon once at install and Android only rechecks it about daily; the OS badge (setAppBadge on iOS, a notification dot on Android) is the only way. Tabs get a drawn favicon badge instead.

Tier 1 limit: the number on the icon only changes while the app is open; Tier 2 adds push so it changes while closed.

On a new phone, messages already in your chats count as unread at first, so the first badge can be large; a fix is planned (KB-1525).

Android TWA

Android

  • + Real store-style icon in hours; same push code as the PWA.
  • - Dot only; needs assetlinks.json in the mchzimm.github.io root repo.

iOS

  • - Android only. Wrapping a web page in an iOS shell gets no web push.

Capacitor

Android

  • + Maintained badge plugin; number on Samsung/Xiaomi.
  • - Dot on Pixel; push to a killed app needs a Kotlin service unless you use notification payloads.

iOS

  • + Real numeric badge, no manual install.
  • - $99; Swift boilerplate pasted in; App Store review risk; no silent push.

Tauri 2

Android

  • + One Rust workspace; small app.
  • - Official count option is dead code; no first-party push (PR stalled).

iOS

  • + Closed-app badge from the server with no Swift.
  • - $99; exact in-app set needs ~10 lines of Swift; push plugin is third-party.

Flutter

Android

  • + Best-kept badge library.
  • - Adds a third language (Dart) and a second socket in Dart.

iOS

  • + Numeric badge, cloud builds.
  • - $99; separate storage means onboarding again.

RN / Expo

Android

  • + One push call covers both phones.
  • - Android number is being removed; badge helper project archived.

iOS

  • + Numeric badge, builds without a Mac.
  • - $99; messages pass through a third-party relay.

6. What to do, in order

  1. PWA tier 1 (~1 day): manifest, tiny service worker, setAppBadge from the unread count. iPhone gets a correct number while the app is open.
    Then tier 2 (3-5 days): the gateway sends Web Push (VAPID). iPhone badge works when closed; Android gets its dot.
  2. Android TWA (hours): store-style icon, same push code, no Firebase.
  3. Capacitor or Tauri 2, only if you pay the $99 and want one of: no manual install on iPhone, a number on Samsung, an always-on Android socket. Capacitor wins on plugin maturity; Tauri wins if staying all-Rust matters.
  4. Flutter or RN, only if the team already knows them. For this goal they add a runtime and gain nothing.

An open mesh socket on iPhone while closed is impossible under every option. On Android it needs a foreground service (a permanent notification).
